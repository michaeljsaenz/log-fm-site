## The Outcome

The management plane runs in a single-node `capi-mgmt` Kind cluster, with two
host services for local dependencies:

- **CAPI** - declarative cluster lifecycle
- **CAPD** - Docker infrastructure provider (runs "nodes" as containers)
- **CAAPH** - HelmChartProxy addon provider for label-matched infrastructure
- **CAAPF** - Fleet addon provider for zero-touch cluster registration
- **Fleet** - the GitOps engine
- **Git daemon** (`:9418`) and **chart server** (`:8879`) on the host, so Fleet
  and CAAPH pull from local sources instead of the internet

## Architecture

The platform runs on one host: a Kind cluster for the controllers, plus a Git
daemon and chart server. No workload clusters are provisioned.

![CAPI management plane with local Git and chart servers](/images/bootstrap-architecture.png)

> - **Zero egress.** Fleet pulls git refs from `:9418`, CAAPH pulls charts from
>   `:8879` - both host-local on the kind bridge. Nothing leaves the machine.
> - **Concurrency.** The management-plane controllers run many informers inside
>   `capi-mgmt`, so host `inotify` limits must be raised before bring-up.

## Nuance

Fleet and CAAPF are installed but idle until a workload cluster exists:

- **Fleet** applies management-plane manifests from local Git. No workload
  cluster is registered, so nothing deploys downstream.
- **CAAPF** imports a CAPI `Cluster` into Fleet after CAPI publishes its
  kubeconfig Secret. No Cluster exists yet, so CAAPF waits.

## Prerequisites

- macOS with OrbStack running
- `docker`, `kind`, `kubectl`, `clusterctl`, `git`, and `make` on `PATH`

## Run & Verify

### Run

```bash
make bootstrap
```

Idempotent and safe to re-run after a container-runtime restart:

- raise `inotify` limits
- create or reuse the `capi-mgmt` Kind cluster
- run `clusterctl init` for CAPI + CAPD + CAAPH + CAAPF (with
  `CLUSTER_TOPOLOGY=true`, required in CAPI v1.13+)
- install Fleet
- start the host git daemon and chart server
- point Fleet's agent callback at the management API

### Verify

```bash
# Management context is live
kubectl cluster-info --context kind-capi-mgmt
# -> Kubernetes control plane is running at https://127.0.0.1:<port>

# All controllers are Running
kubectl get pods -A | grep -E "capi|capd|caaph|caapf|fleet"
# -> caapf-controller-manager      2/2   Running
# -> caaph / capd / capi-* managers 1/1   Running
# -> fleet-agent, fleet-controller (3/3), gitjob, helmops   Running

# Chart server is up (reachable by cluster pods on the kind network at :8879)
docker ps | grep chart-server
# -> chart-server   Up   (no host port published; kind-network only)

# Git daemon serves the repo's committed refs on :9418
git ls-remote git://localhost/capi-local-lab
# -> <sha>   HEAD        (plus every ref in your clone)

# Management node is Ready
kubectl get nodes --context kind-capi-mgmt
# -> capi-mgmt-control-plane   Ready   control-plane   v1.36.1
```

## Key Insights

- **Raise `inotify` limits.** Defaults can cause controllers to silently drop
  reconcile events. Set:
  `fs.inotify.max_user_watches=524288`, `fs.inotify.max_user_instances=512`.
- **Keep the control plane disposable.** `make destroy` removes it; `make bootstrap`
  rebuilds it.
- **Use local dependencies.** Git serves committed refs on `:9418`; the chart
  server serves charts on `:8879`. No egress required.
- **Refresh kubeconfig after runtime restarts.** Kind's API port can change. Run
  `kind export kubeconfig --name capi-mgmt` or `make bootstrap`.
