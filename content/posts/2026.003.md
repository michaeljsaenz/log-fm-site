## The Outcome

The `hello-world` app runs on `local-cluster`:

- **App:** Two-replica `nginx:alpine` Deployment with ClusterIP Service.
- **GitRepo:** `apps` targets clusters labeled `environment=local`.
- **Agent:** Workload-cluster `fleet-agent` pulls the app; the management plane does not push to it.

> Fleet's management-plane `gitjob` clones app manifests from the host Git daemon
> on port `9418` and renders them into a `Bundle`. The workload-cluster agent
> pulls the Bundle from Fleet, so no remote Git access is needed.

## Architecture

CAAPF registers the cluster with Fleet and propagates its labels. Fleet's `gitjob` clones the committed ref and renders a `Bundle`. The `apps` GitRepo scopes its `BundleDeployment` to clusters matching `environment=local`, where `fleet-agent` pulls and applies it.

![Zero-touch app delivery on one host: the apps GitRepo in capi-mgmt renders a hello-world Bundle, Fleet scopes a BundleDeployment to local-cluster by environment=local, and the downstream fleet-agent pulls it from the management cluster](/images/onboarding-architecture.png)
> - **Label-scoped.** The CAPI `Cluster` carries `environment=local`; CAAPF copies
>   that label onto the Fleet `Cluster` it registers, and the `apps` GitRepo's
>   `clusterSelector` matches on it. A cluster receives the app by wearing the
>   label, not by being named in the GitRepo.


## Nuance

Delivery depends on two placement rules:

- **Namespace:** A `GitRepo` only targets clusters in its own namespace. CAAPF registers the cluster in `default`, so `apps` must live there, not in `fleet-local` (namespace Fleet uses for its management cluster).
- **Committed Refs Only:** Fleet clones committed refs, not working trees. `make onboard` blocks until manifests are committed.


Scaling is just more commits and labels: a second app is another path in the
`GitRepo`; labeling another cluster `environment=local` delivers the app there
too.

## Prerequisites
- [capi-local-lab](https://github.com/michaeljsaenz/capi-local-lab) cloned locally (featuring the `p2/` scripts and manifests).
- A running management plane and provisioned workload cluster (`make bootstrap` and `make provision`; see [Provisioning a CAPI Workload Cluster with Fleet]({{< ref "/posts/2026.002.md" >}})).

## Run & Verify

### Run

```bash
make onboard
```
Requires `make provision` first. See [Provisioning a CAPI Workload Cluster with Fleet]({{< ref "/posts/2026.002.md" >}}). In order it:

- checks local tooling and the management context
- checks for a registered cluster labeled `environment=local`
- applies the `apps` GitRepo after the manifests are committed

The management Fleet clones the committed ref and renders a `Bundle`. The
workload-cluster `fleet-agent` pulls and applies it.

### Verify

Check the delivery directly:

```bash
# Confirm the apps GitRepo and its BundleDeployments are ready
kubectl get gitrepo apps -n default
# -> apps   git://host.docker.internal/capi-local-lab   <sha>   1/1

# The hello-world bundle is deployed to the registered cluster
# Bundle name combines the GitRepo name and committed path
kubectl get bundles -n default
# -> apps-<path>-hello-world     1/1
# -> fleet-agent-local-cluster   1/1

# On the workload cluster, the app is Running
# Kubeconfig comes from `make verify CLUSTER=local-cluster`
KUBECONFIG=/tmp/local-cluster-kubeconfig kubectl get deploy,svc -l app=hello-world
# -> deployment.apps/hello-world   2/2   ...
# -> service/hello-world           ClusterIP ...
```

## Key Insights


- **Pull vs. Push**: Addons push via CAAPH (helm install); apps pull via fleet-agent.
- **Label Membership** Onboarding uses environment=local labels instead of custom pipelines.
- **Namespace must match.** The `GitRepo` and the registered cluster share a
  namespace (`default`), or the target never matches.
- **Commit, not working tree.** Fleet serves committed refs; `make onboard` fails
  fast on uncommitted changes.
- **Self-contained.** 
`make onboard` pairs with `make offboard` (removes apps, leaves cluster intact).
