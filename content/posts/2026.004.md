## The Outcome

Two clusters with distinct roles, plus an app:

- **Management cluster** - `capi-mgmt` (Kind) runs CAPI + CAPD, CAAPH, CAAPF,
  and Fleet. It declares and manages clusters; no apps run here.
- **Workload cluster** - `local-cluster`: a load balancer, one control plane,
  and two workers as Docker containers, hydrated with Cilium, cert-manager, and
  ingress-nginx, plus one `fleet-agent`.
- **App** - `hello-world` (two `nginx:alpine` replicas and a ClusterIP Service),
  delivered by GitOps alone.

## Architecture

The management cluster holds the desired state; the workload cluster is what
that state becomes:

![Local CAPI + Fleet platform: the capi-mgmt management cluster runs CAPI, CAPD, CAAPH, Fleet, and CAAPF and holds the Cluster CR; from it, CAPI and CAPD provision the separate local-cluster workload cluster (load balancer, control plane, two workers), CAAPH pushes Cilium, cert-manager, and ingress-nginx into it, CAAPF installs one fleet-agent, and that agent pulls hello-world; the host chart server and git daemon feed the management cluster](/images/assembling-architecture.png)

- **Host** - a git daemon (`:9418`) serves the committed manifests; a chart
  server (`:8879`, on the kind network) serves the addon charts.
- **Management** - Fleet delivers the `local-cluster` `Cluster` CR and the
  `hello-world` Bundle; CAPI + CAPD turn the CR into nodes. The CR's labels
  drive the rest: `cni`, `tls`, and `ingress` select CAAPH's addons, and
  `environment=local` (copied into Fleet by CAAPF) selects the app.
- **Workload** - addons arrive from CAAPH; the app arrives through its own
  `fleet-agent`.

## Nuance

- **Namespaces must line up.** CAAPF registers the workload cluster into Fleet in
  `default`, beside its CAPI `Cluster`, so the `apps` GitRepo lives there too.
  The `capi-clusters` GitRepo lives in `fleet-local` because it targets the
  management cluster itself.
- **Each layer waits on the last.** CAAPH's webhook serves only after it is
  installed, nodes go Ready only once Cilium lands, and apps can target the
  cluster only after CAAPF registers it. Every `make` step returns before its
  controllers converge, so `make up` waits between steps.

## Prerequisites

- **Container runtime** - OrbStack (recommended) or Docker Desktop with at least
  8 GB memory and 4 CPUs (12-16 GB and 6-8 CPUs recommended).
- **CLI tools** - `docker`, `kind`, `kubectl`, `clusterctl`, `helm`, `git`,
  `envsubst` (from `gettext`), and `python3`. `make up` checks for all of them
  before it starts.
- **Committed manifests** - Fleet clones committed refs, never the working tree,
  so the cluster and app manifests must be committed on the current branch.
- **Internet access** - `clusterctl` provider manifests, the Fleet chart, and
  container images (Kind, Cilium, cert-manager, ingress-nginx, `nginx:alpine`)
  come from public sources; only git and the addon charts are served from the
  host.

## Run & Verify

### Run

```bash
make up
```

Runs `make bootstrap`, `make provision`, and `make onboard` in order, waiting
between each on the controllers' own status:

![make up flow: make bootstrap, make provision, and make onboard run in order, each followed by readiness gates - providers up and webhooks answering, then local-cluster delivered and Available, addons deployed, and Fleet registration, then make verify, then app bundles ready and rollout - while make down runs make offboard, make deprovision, and make destroy in reverse](/images/assembling-make-up-flow.png)

A clean run takes about four minutes; a re-run on a running platform takes
seconds. A stalled wait times out after `WAIT_TIMEOUT` seconds (default `900`),
and re-running resumes where it stopped.

Tear it all down (`make offboard`, `make deprovision`, then `make destroy`):

```bash
make down
```

### Verify

`make up` reports `Platform ready` only once every layer has converged. Check
the end state directly:

```bash
# Management cluster: the workload cluster is Available, nodes Running
kubectl get cluster local-cluster -n default
# -> local-cluster   quick-start   True   1 1 1   2 2 2   Provisioned   ...
kubectl get machines -n default
# -> local-cluster-...   Running   (x3: 1 control plane, 2 workers)

# Management cluster: addons deployed by CAAPH
kubectl get helmreleaseproxy -n default
# -> cert-manager-local-cluster-...    True   deployed
# -> cilium-local-cluster-...          True   deployed
# -> ingress-nginx-local-cluster-...   True   deployed

# Management cluster: workload cluster registered into Fleet, both GitRepos ready
kubectl get cluster.fleet.cattle.io -n default
# -> local-cluster   2/2   <recent LAST-SEEN>
kubectl get gitrepo -A
# -> default       apps            git://host.docker.internal/capi-local-lab   <sha>   1/1
# -> fleet-local   capi-clusters   git://host.docker.internal/capi-local-lab   <sha>   1/1

# Workload cluster (kubeconfig written by make up)
export KUBECONFIG=/tmp/local-cluster-kubeconfig
kubectl get nodes
# -> local-cluster-...   Ready   control-plane   ...
# -> local-cluster-...   Ready   <none>          ...   (x2)
kubectl get deploy,svc -l app=hello-world
# -> deployment.apps/hello-world   2/2   ...
# -> service/hello-world           ClusterIP   ...   80/TCP
```

After `make down`, the host is bare again:

```bash
kind get clusters
# -> No kind clusters found.
```

## Key Insights

- **Separate the manager from the managed.** The management cluster holds only
  desired state, so every workload cluster is reproducible from it - delete a
  worker `Machine` and its MachineDeployment replaces it.
- **Labels are the API.** A differently shaped cluster is a label edit, not a
  new pipeline.
- **Push for infra, pull for apps.** CAAPH installs infrastructure from above;
  the `fleet-agent` pulls apps from below, so app delivery never needs the
  management cluster to reach in.
- **Gate on status, not time.** Read the conditions controllers publish
  (`Available`, `deployed`, agent `lastSeen`, ready bundles) instead of
  sleeping; recovering from a stalled step is then just the same command again.
- **Host-local sources.** Fleet and CAAPH read only committed refs from `:9418`
  and charts from `:8879`, so what gets deployed is exactly what is committed -
  never an external git or chart repo.
